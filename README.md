# deployctl

Самостоятельная утилита сборки и развёртывания Go-приложений. Реализация ведётся по `doc/DEPLOYCTL_ROADMAP.md`.

## Установка

Актуальную опубликованную версию устанавливайте через Go:

```powershell
go install github.com/LittleDrongo/deployctl@latest
deployctl version
```

Для рабочей машины `@latest` — основной способ установки и обновления. В CI и других воспроизводимых сценариях указывайте конкретный тег, например `@v1.0.0`, чтобы новая версия CLI не изменила сборку без изменения проекта. Для приватного репозитория настройте `GOPRIVATE=github.com/LittleDrongo/*` и Git-доступ до запуска `go install`.

Для машины без Go proxy скачайте архив своей ОС и архитектуры из GitHub Release, проверьте его по `SHA256SUMS`, распакуйте `deployctl`/`deployctl.exe` в каталог из `PATH` и выполните `deployctl version`. Workflow `.github/workflows/release.yml` по тегам `vM.N.P` тестирует проект и выпускает архивы для Windows, Linux и macOS на `amd64` и `arm64`; ручной запуск workflow создаёт только проверяемые CI-артефакты и не публикует Release.

Доступны:

```powershell
go run . version
go run . info
go run . info --root C:\path\to\application --json
go run . init --root C:\path\to\application --dry-run
go run . init --root C:\path\to\application
go run . config check --root C:\path\to\application
go run . doctor prod --root C:\path\to\application
go run . build --root C:\path\to\application --platform windows-amd64
go run . build --root C:\path\to\application --platform linux-amd64 --dry-run
go run . build --root C:\path\to\application --platform linux-amd64 --tag v1.0.0
go run . up prod --root C:\path\to\application --dry-run
go run . release --root C:\path\to\application --dry-run
go run . clean --root C:\path\to\application --dry-run
go build -o .bin/deployctl.exe .
```

`version` показывает версию CLI (по умолчанию `dev`, задаётся при выпуске через `-ldflags "-X main.version=vX.Y.Z"`). `info` показывает версию приложения: тег на HEAD, `<tag>-dev` после тега, дополнительный `-dirty` при локальных изменениях. Без тегов используется `dev-g<short-hash>`, вне Git — `dev`. Git-репозиторий должен содержать хотя бы один коммит; ошибки чтения Git возвращаются пользователю.

Корень приложения определяется по ближайшему `go.mod` вверх от текущего каталога. Вложенный модуль имеет приоритет над родительским; `go.work` не меняет выбор. `--root` указывает каталог с `go.mod` явно; относительный путь отсчитывается от текущего каталога терминала.

`build` сохраняет бинарник в `<root>/.bin/<app>-<version>-<platform>` (с `.exe` для Windows). Имя приложения берётся из пути модуля без завершающего `/v2`, `/v3` и т. п. Добавьте `/.bin/` в `.gitignore` приложения, чтобы результаты сборки не делали рабочее дерево dirty. Существующий артефакт заменяется только после успешной компиляции.

По умолчанию собирается пакет `.` для платформ из `build.platforms` в порядке списка. Без списка используется старое поле `build.platform`, а без обоих полей — текущая ОС и архитектура. `--platform` выбирает только одну платформу вместо списка. Ошибка одной сборки не мешает остальным; если были ошибки, команда возвращает ненулевой код. Прерывание останавливает оставшиеся сборки. `--package ./cmd/server` выбирает другой main-пакет внутри модуля. `--timeout 20m` ограничивает продолжительность операции. Используются `CGO_ENABLED=0`, `GOWORK=off`, `-trimpath` и `-mod=readonly`: зависимости должны быть подготовлены заранее, `go.mod` и `go.sum` автоматически не обновляются. Для приложений с обязательным CGO этот режим не подходит.

Метаданные внедряются в `github.com/LittleDrongo/buildcard` и, для совместимости со старыми приложениями, в `<module>/internal/buildinfo`, если эти пакеты входят в зависимости выбранного main-пакета. Приложение должно использовать API метаданных, например `buildcard.Snapshot()`. Версия, коммит, дата коммита, dirty-состояние и время сборки задаются CLI; поле репозитория пока содержит путь модуля приложения. Если поддерживаемых пакетов нет, сборка продолжается с предупреждением. Сам CLI не добавляет библиотеку в приложение.

`--tag` выбирает локальный тег (также поддерживается вариант имени с префиксом `v` или без него). Сборка выполняется в отдельном временном Git worktree, который затем удаляется; текущая ветка, индекс и файлы пользователя сохраняются. Используются исходники и зависимости выбранного тега, результат попадает в `.bin` текущего приложения. Абсолютные `replace` и относительные ссылки за пределы checkout требуют отдельно доступных зависимостей.

`--dry-run` показывает план без запуска Go, создания артефактов или изменения Git. Он не проверяет доступность зависимостей и поддержку платформы компилятором; эти проверки выполняются при реальной сборке. Во время обычной сборки не редактируйте исходники: проверка изменения их содержимого в ходе компиляции пока не реализована.

`init` создаёт `service.yaml`, добавляет `/.bin/` в `.gitignore` и подключает `github.com/LittleDrongo/buildcard@v1.0.0` через `go get`, если зависимости ещё нет. Для первого подключения нужен доступ к Go proxy или заполненный кеш. Уже указанная версия и директивы `replace` сохраняются; автоматического обновления или понижения версии нет. `go get` может изменить `go.mod` и `go.sum`, как при ручном подключении пакета.

Новый `service.yaml` содержит все девять платформ в `build.platforms`: windows-amd64, windows-arm64, linux-amd64, linux-arm64, android-arm64, windows-386, linux-386, darwin-amd64, darwin-arm64. Ненужные элементы можно закомментировать или удалить; для возврата к платформе машины задайте `platforms: []` или удалите поле целиком. Поддержка конкретной сборки зависит от Go и зависимостей приложения; включение платформы в шаблон не гарантирует совместимость приложения с ней.

Новый `service.yaml` использует `alpine:3.20` как `docker_base_image`. Значение можно явно заменить для конкретного приложения или target.

`init --dry-run` показывает будущие файлы и добавляемые строки, не записывая их и не загружая зависимости. Существующий YAML проверяется и сохраняется; ошибочный конфиг нужно исправить перед инициализацией. Повторный запуск не дублирует настройки. `--scaffold` создаёт тихий пример `main.go` с `buildcard.Snapshot()`, только если файла ещё нет; `--makefile` создаёт необязательную оболочку для `build` и `info`. Исходники существующего приложения автоматически не редактируются.

Конфиг по умолчанию — `service.yaml` в корне модуля. Имя не совпадает с префиксом команды `deployctl` при автодополнении файлов. Первая строка создаваемого конфига содержит `go install github.com/LittleDrongo/deployctl@latest`. Для совместимости, если `service.yaml` отсутствует, используется прежний `deploy.yaml`; `init` сохраняет такой файл и не создаёт рядом второй. При наличии обоих приоритет у `service.yaml`. Явный `--config` отменяет автоматический выбор. `--config` в `init`, `build` и `config check` выбирает другой файл; относительный путь всегда отсчитывается от корня модуля, а не от текущего подкаталога. `build` работает и без конфига; явно указанный файл должен существовать. Параметры CLI перекрывают `build.package` и выбор платформ (`build.platforms` или прежнее `build.platform`); `--tag` использует текущий конфиг, а исходники берёт из выбранного тега.

Минимальный конфиг для локальной сборки:

```yaml
version: 1
build:
  package: .
  platform: windows-amd64
targets: {}
```

Схема и пример настройки сервера описаны в [doc/CONFIG.md](doc/CONFIG.md). `config check` проверяет структуру и значения всех targets без подключения к SSH или Docker. Неизвестные поля, повторяющиеся ключи, `null`, YAML aliases/merge и несколько документов отклоняются. `init` оставляет `targets: {}` и пример SSH-алиаса в комментариях: адрес сервера следует указать самостоятельно.

`up <target>` собирает приложение для `build_target` выбранного сервера, передаёт бинарник по SCP и запускает транзакцию по SSH. Поддерживаются `--root`, `--config`, `--package`, `--tag`, `--timeout` (таймаут сборки), `--dry-run` и `--keep-artifact`. После успешного деплоя локальный бинарник удаляется, если не задан `--keep-artifact`; при ошибке сохраняется. Docker-тег соответствует версии приложения; без Git-тегов используется `dev` или `dev-dirty`.

`doctor <target>` без изменений на сервере проверяет наличие локальных `ssh` и `scp`, удалённых `sh`, `docker`, `flock`, `timeout`, `sha256sum`, доступ текущего SSH-пользователя к Docker daemon, наличие базового образа и доступность `remote_dir` и путей монтирования. Для отсутствующих путей с `create_host_path` проверяется возможность создания через ближайший существующий родитель. Команда показывает удалённые UID/GID и собирает все найденные проблемы за один запуск. Если базового образа нет, выводятся команды для `docker pull` или переноса через `docker save`, SCP и `docker load`. Эти же инструкции выводятся при ошибке подготовки runtime-образа во время `up`. `doctor --dry-run` только показывает план и не подключается по SSH.

Транзакция проверяет SHA-256, блокирует контейнер и каталог, подготавливает runtime-образ, резервирует предыдущий бинарник и контейнер, заменяет бинарник и проверяет готовность. С healthcheck ожидается `healthy`; без него проверяется только стабильность процесса, а не прикладная готовность. При ошибке выводятся состояние, код завершения и последние 100 строк stdout/stderr неудачного контейнера до удаления, затем восстанавливается предыдущее состояние. Сбой чтения логов не мешает откату. Если откат не завершён, резервный бинарник сохраняется и выводится его путь.

После успешного запуска очищаются старые образы только данного репозитория. Текущий образ, образы других имён и образы, используемые контейнерами, сохраняются; глобальный prune и принудительное удаление образов не используются. Runtime-образ содержит среду, а бинарник монтируется с сервера; Docker-тег сам по себе не является полным артефактом релиза.

`stop <target>` останавливает контейнер без удаления. `restart <target>` перезапускает существующий контейнер и проверяет готовность; отсутствующий не создаёт. `remove <target>` останавливает и удаляет только контейнер, сохраняя образы, бинарник и данные. Отсутствующий контейнер для `stop`/`remove` считается уже обработанным. Эти команды также поддерживают `--root`, `--config` и `--dry-run`.

Для работы с Windows достаточно системных `ssh` и современного `scp` с SFTP в PATH; Make/Bash/WSL для запуска CLI не нужны. Псевдоним `host` передаётся OpenSSH напрямую. При отсутствии `user` и `port` CLI не переопределяет их из SSH config. Используется `BatchMode=yes`: ключ/агент и known_hosts должны быть подготовлены заранее. На Linux-сервере нужны Docker, `sh`, `flock`, GNU `timeout`, `sha256sum` и стандартные файловые утилиты; SSH-пользователю нужны права на Docker и настроенные каталоги. Права bind-монтирований должны позволять выбранному UID контейнера читать бинарник и данные.

SSH-пользователь выполняет файловые операции deployctl на сервере и обращается к Docker daemon. По умолчанию `container_user: ssh`: контейнер запускается с числовыми UID/GID этого же пользователя, полученными на сервере, поэтому обычные конфиги и данные приложения принадлежат ему и редактируются без sudo. Значение `container_user: image` сохраняет пользователя базового образа; явный `--user`/`-u` в `docker_run_args` имеет приоритет над этой настройкой. Поле наследуется из `defaults`, а `init` показывает его явно. Если SSH выполняется от root, файлы также будут принадлежать root.

Служебные каталоги и файлы остаются защищены `umask 077`. Переход с прежнего поведения вызывает новый деплой даже при том же бинарнике. Существующие файлы от root автоматически не меняют владельца: это нужно сделать отдельно для конкретных файлов сервиса, например `sudo chown "$(id -u):$(id -g)" /srv/app/config.yaml`, выполнив команду под нужным SSH-пользователем. Для существующего каталога аналогично исправьте владельца самого каталога; не применяйте рекурсивный chown к посторонним данным или системным сертификатам. Процесс приложения может сам менять права файлов, поэтому этот режим не отменяет его собственные chmod/chown. При явном отдельном UID контейнера доступ к каталогам нужно настроить самостоятельно.

Корпоративные CA лучше включать в отдельный базовый образ. Для Ubuntu сертификаты обычно устанавливают в `/usr/local/share/ca-certificates` и запускают `update-ca-certificates`; для Oracle Linux используют `/etc/pki/ca-trust/source/anchors` и `update-ca-trust`. Готовый bundle также можно передать как bind-mount по пути, который читает конкретное приложение. Deployctl не запускает эти команды автоматически и не отключает проверку TLS. Часовой пояс контейнера задавайте явно через `TZ` в `docker_run_args` или подготовленный образ; локальный часовой пояс SSH-машины автоматически не наследуется.

При enforcing SELinux каталоги bind-mount должны иметь разрешённый контекст. Текущий формат `docker_mounts` не выполняет автоматическую relabel-операцию `:z`/`:Z`; постоянный контекст настраивает администратор сервера через политику SELinux и `semanage fcontext`/`restorecon`. Deployctl не отключает SELinux.

Docker-образы и Go-модули загружаются из разных источников. Зеркало Docker registry не заменяет Go proxy или Git-доступ, необходимый `go get`, `go mod download` и сборке; Go proxy, `GOPRIVATE` и доступ к приватным репозиториям настраиваются отдельно. Для закрытой сети зависимости Go следует заранее поместить в кеш или внутренний proxy, а базовый Docker-образ — во внутренний registry либо перенести через `docker save`/SCP/`docker load`.

Оба потока SSH проходят фильтрацию известных значений аргументов и распространённых форм паролей/DSN. Строки длиннее 64 KiB целиком скрываются. Приложение также должно избегать вывода секретов: произвольные форматы и кодировки не могут быть надёжно распознаны фильтром.

Транзакция проверена локально с настоящим shell и файловыми операциями, с имитацией Docker, блокировок и времени, а также на тестовом сервере `mini` с реальными SSH, SCP и Docker. Проверены первый деплой, повторное обновление, `stop`, `restart`, `remove`, отказ `restart` при отсутствующем контейнере и восстановление после ошибки DSN, panic, завершения без логов и цикла перезапусков. После каждого сбоя восстанавливались прежний контейнер и SHA-256 бинарника; тестовый секрет в диагностике скрывался. Перед использованием на другом сервере сначала просмотрите `up --dry-run`.

`release` требует чистое рабочее дерево, Git-репозиторий с коммитом, отсутствие релизного тега на `HEAD`. Наличие `origin` необязательно: сначала создаётся локальный тег, затем при наличии `origin` выполняется отправка. Без `origin` команда успешно завершается с сообщением, что тег сохранён только локально; другие remotes не используются вместо `origin`. Ближайший достижимый тег `vM.N.P` или старого вида `M.N.P` ищется от `HEAD` назад по времени пакетами по 10 коммитов. Поиск прекращается на первом коммите с релизным тегом; всё множество тегов репозитория не перебирается. Если на этом коммите несколько релизных тегов, выбирается максимальная версия. Без найденного тега создаётся `v1.0.0`; после `.99` увеличивается minor. Команда отправляет только созданный тег через `--no-follow-tags`. При ошибке push локальный тег сохраняется, а в ошибке печатается команда повторной отправки. `release --dry-run` выполняет проверки, показывает следующий тег и план отправки без изменения Git. Ошибка отправки в настроенный `origin` остаётся ошибкой команды, а не считается локальным успехом.

`clean` удаляет только каталог `.bin` непосредственно в найденном корне Go-модуля. `clean --dry-run` показывает путь без удаления. Отсутствующий каталог считается уже очищенным. Если `.bin` является symlink, junction или объектом другого типа, команда отказывается выполнять очистку.

Старый `deploy/deploy_config.yaml` не поддерживается и автоматически не преобразуется. Для приложения создайте новый `service.yaml` командой `deployctl init`, заполните его по актуальной схеме и проверьте через `deployctl config check`.

## Переход приложения

1. Установите deployctl через `@latest`; в CI зафиксируйте проверенный релизный тег.
2. Выполните `deployctl init` в корне Go-модуля. Старый YAML не копируйте: заполните новый корневой `service.yaml` по актуальной схеме.
3. Замените использование локального `internal/buildinfo` на `github.com/LittleDrongo/buildcard`: получайте данные через `buildcard.Snapshot()` и вызывайте `Preview()` только там, где таблица действительно нужна.
4. Выполните `deployctl config check`, `deployctl doctor <target>` и `deployctl up <target> --dry-run`, затем тестовое развёртывание.
5. После успешной проверки удалите старые исходники `deploy/` и команды Makefile, которые вызывали прежний механизм. На переходном коммите Makefile может вызывать новый deployctl с зафиксированной версией.

Проверки: `go test ./...` и `go vet ./...`. Для тестов Git-метаданных нужен Git в PATH; транзакционные тесты используют Bash (на Windows — Git Bash), при его отсутствии пропускаются. Для чтения метаданных проекта вне Git установка Git не требуется.

## Просмотр состояния

`deployctl status prod` показывает одну строку таблицы для выбранного target. `deployctl status` опрашивает все targets из `service.yaml` и выводит их в порядке имени. Колонки: target, контейнер, состояние, запуск, перезапуск, health, код выхода, образ, число перезапусков и время создания. Отсутствующий контейнер обозначается `absent`. Если один сервер недоступен, его строка показывает `ошибка`, остальные всё равно проверяются; команда завершается с ошибкой. `--dry-run` перечисляет targets без SSH.

## Цветной вывод

В локальном терминале сообщения «Обновление отменено» и «Откат не завершён» выделяются белым текстом на красном фоне. В `status` состояние `running` зелёное, остальные состояния красные; Health `healthy` зелёный, `unhealthy` красный, `starting` жёлтый, `none` без цвета. Цвет добавляется после фильтрации секретов. При перенаправлении вывода, непустой переменной `NO_COLOR` или `TERM=dumb` управляющие коды не добавляются; `logs` не перекрашивает сообщения приложения.

## Автодополнение Bash на Linux

`go install` устанавливает бинарник, но не запускает post-install скрипты и не изменяет окружение родительского shell. После установки CLI один раз выполните:

```bash
deployctl completion install bash
source "${XDG_DATA_HOME:-$HOME/.local/share}/bash-completion/completions/deployctl"
```

При установленном и подключённом `bash-completion` файл автоматически загружается в новых сеансах Bash. Если `bash-completion` не используется, добавьте строку `source` из примера в `~/.bashrc`. Команда установки сама не меняет `.bashrc` и не требует sudo; повторный запуск обновляет только файл, созданный deployctl. Также можно загрузить скрипт без установки: `source <(deployctl completion bash)`.

Примеры: `deployctl st<TAB>` предлагает `status` и `stop`; `deployctl up p<TAB>` предлагает targets текущего проекта; `deployctl up prod --k<TAB>` предлагает `--keep-artifact`; `deployctl build --platform linux-a<TAB>` предлагает архитектуры. Учитываются `--root`, `--config`, вложенные каталоги проекта и старый `deploy.yaml`. При отсутствующем или ошибочном конфиге targets не предлагаются. Автодополнение читает только локальные файлы, не выполняет SSH, сборку или загрузку зависимостей. Сейчас поддерживается Bash; это не скрипт для Zsh или Fish.
