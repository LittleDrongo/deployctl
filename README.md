# deployctl

Собирает Go-приложение на машине разработчика и развёртывает его через SSH и Docker. Go и исходники на сервере не нужны.

## Начало работы

В существующем Go-модуле:

```bash
go install github.com/LittleDrongo/deployctl@latest
deployctl init
```

`init` создаёт `config_deploy.yaml`, добавляет `/.bin/` в `.gitignore` и подключает `buildcard`. В новом конфиге перечислены девять платформ: удалите или закомментируйте ненужные. Заполните `targets` для своих серверов; схема и пример — в [doc/CONFIG.md](doc/CONFIG.md). Если используется старый `deploy.yaml`, он продолжит работать, пока рядом нет `config_deploy.yaml`.

```bash
deployctl config check
deployctl build
deployctl doctor prod
deployctl up prod --dry-run
deployctl up prod
deployctl status
```

Перед `up` серверу нужны SSH-доступ по ключу, Docker без `sudo` для SSH-пользователя и базовый образ из `docker_base_image`. `doctor` проверяет окружение и подсказывает, как перенести образ на сервер без доступа к registry.

## Команды

Для новых проектов `init` подключает `buildcard v1.0.2`. Уже существующую зависимость он сохраняет; обновите её в проекте приложения командой `go get github.com/LittleDrongo/buildcard@v1.0.2`. При сборке deployctl встраивает URL Git `origin` в поле репозитория и манифест (без URL-пароля и query-параметров); если `origin` отсутствует, используется путь Go-модуля.

| Команда | Действие |
| --- | --- |
| `init` | Подготовить модуль и конфиг; `--scaffold` создаёт пример `main.go`, `--makefile` — Makefile. |
| `info` | Показать версию приложения из Git. |
| `build` | Собрать платформы из конфига в `.bin`; `--platform` выбирает одну. |
| `doctor <target>` | Проверить сервер перед деплоем. |
| `up <target>` | Собрать, передать и запустить приложение. |
| `status [target]` | Показать таблицу для одного или всех targets. |
| `logs <target>` | Показать логи; `--follow` следит за новыми строками. |
| `stop`, `restart`, `remove <target>` | Управлять контейнером. |
| `release` | Создать локальный тег и отправить его, если настроен `origin`. |
| `clean` | Удалить локальный каталог `.bin`. |

`--root` указывает каталог Go-модуля, `--config` — файл конфигурации, `--dry-run` показывает план. Без `--root` ищется ближайший `go.mod`. Для сборки существующего тега используйте `build --tag v1.0.0` или `up prod --tag v1.0.0`. После успешного `up` локальный бинарник удаляется; `--keep-artifact` оставляет его в `.bin`.

При ошибке запуска `up` выводит состояние и последние строки логов, затем восстанавливает прежний контейнер и бинарник. Без Docker healthcheck проверяется стабильность процесса, а не готовность приложения. `status` показывает недоступный target как ошибку и продолжает проверять остальные.

По умолчанию контейнер работает от пользователя базового образа (`container_user: image`); в `alpine:3.20` это root. Созданные им файлы на хосте могут требовать `sudo` для редактирования. Для запуска с UID/GID SSH-пользователя явно задайте `container_user: ssh`. Существующие владельцы и права файлов автоматически не меняются. Серверный бинарник остаётся в смонтированном каталоге: Docker-образ содержит среду, но не сам бинарник.

В существующем конфиге замените `container_user: ssh` на `container_user: image` и выполните `up` обновлённой утилитой. Удалите явный `--user`/`-u` из `docker_run_args`, если он задан: такой аргумент имеет приоритет. Членство в группе `docker` не даёт права редактировать root-owned файлы на хосте. Каталоги вне монтирований (например, `/.config`) исчезнут при пересоздании контейнера; для сохранения конфигурации оставьте `HOME=/app` и `XDG_CONFIG_HOME=/app/.config` через `--env` в `docker_run_args`.

В режиме `container_user: ssh` домашний каталог (`HOME`) и каталоги XDG для конфигурации, кэша, данных и состояния направлены в смонтированный каталог приложения (обычно `/app`). Это позволяет библиотекам создавать `.config`, `.cache` и `.local` с правами SSH-пользователя. Значения можно переопределить через `--env` или `--env-file` в `docker_run_args`. Доступ к произвольным системным каталогам контейнера не предоставляется.

Каталог приложения должен быть доступен SSH-пользователю для записи и входа. При `container_user: image` или явном `--user`/`-u` домашний каталог и XDG-пути автоматически не задаются. При переопределении `HOME` укажите также нужные XDG-пути: они абсолютные. После обновления deployctl следующий `up` пересоздаст контейнер со старой политикой окружения даже для той же версии приложения; `restart` окружение не обновляет.

При создании контейнера deployctl передаёт `BUILDCARD_CONTAINER=true`, `BUILDCARD_CONTAINER_HOST` (имя Docker daemon), `BUILDCARD_CONTAINER_USER` (SSH-пользователь деплоя), `BUILDCARD_CONTAINER_NAME` и `BUILDCARD_CONTAINER_IMAGE`. Версия buildcard с поддержкой этих полей выводит их в снимке отдельно от имени машины и пользователя процесса. Для существующего контейнера окружение обновляется через `up`, а не `restart`.

## Автодополнение Bash

```bash
deployctl completion install bash
source "${XDG_DATA_HOME:-$HOME/.local/share}/bash-completion/completions/deployctl"
```

Установка через `go install` не настраивает shell. Если `bash-completion` подключён, в новых сеансах установленный файл загружается автоматически. Для CI фиксируйте проверенный тег deployctl вместо `@latest`.
